# Xilinx synthesis reports

`xilinx_reports.exe` uses
[`hardcaml_xilinx_reports`](https://github.com/janestreet/hardcaml_xilinx_reports) to
generate out-of-context Vivado projects and summarize timing and primitive utilization.
It is separate from `lib/common/generate.exe`: the reports library emits its own Verilog,
clock XDC, Tcl, and report artifacts for each selected circuit.

The available targets are:

| Target | Hardcaml circuit |
| --- | --- |
| `tx-crc` | `Tx_crc` |
| `rx-crc` | `Rx_crc` |
| `tx-controller` | `Tx_controller` |
| `rx-controller` | `Rx_controller` |
| `mac-rx-path` | `Mac_rx_path` |
| `mac-tx-path` | `Mac_tx_path` (IPv4 ethertype) |
| `udp-ipv4-tx` | `Udp_duplex_mac_top.Tx_path` |
| `udp-ipv4-rx` | `Udp_duplex_mac_top.Rx_path` |
| `mac-top` | `Mac_top` (hardware RX async FIFO, IPv4 ethertype) |
| `udp-duplex-mac-top` | `Udp_duplex_mac_top` (hardware RX async FIFO) |

## Inspect or generate a project

Show the available targets and the flags generated by the reports library:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- -help
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- tx-crc -help
```

Generate a project without launching Vivado:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- tx-crc \
  -dir _build/xilinx-reports/dry-run \
  -part xc7a100tcsg324-1 \
  -clock clock:25
```

Generated files are written below a circuit-named subdirectory, such as
`_build/xilinx-reports/dry-run/tx_crc/`. They remain untracked because `_build/` is
ignored.

Standard Vivado utilization and timing reports are always enabled by this wrapper. The
upstream `-reports` flag remains visible for compatibility, but it is not necessary.

After Vivado finishes, the command prints a curated utilization table, the Vivado setup,
hold, and pulse-width summary, and the paths of all report artifacts. Add `-full-report`
to print the complete standard utilization and timing reports directly to the terminal.

The compact report contains timing data, but its upstream primitive-group queries are
designed for UltraScale devices and return zero utilization on `xc7a100t`. To avoid
displaying a convincing but incorrect zero table, this executable disables the compact
primitive groups. The generated standard `post_synth_<circuit>.utilization` file is the
authoritative resource report.

## Run report profiles

Timing-oriented profile, including the design hierarchy below the selected circuit:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- tx-crc \
  -dir _build/xilinx-reports/timing/tx-crc \
  -part xc7a100tcsg324-1 \
  -clock clock:25 \
  -hierarchy \
  -full-design-hierarchy true \
  -jobs 1 \
  -run
```

Resource-oriented profile, black-boxing any child circuits while each circuit is
synthesized independently:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- tx-crc \
  -dir _build/xilinx-reports/resources/tx-crc \
  -part xc7a100tcsg324-1 \
  -clock clock:25 \
  -hierarchy \
  -full-design-hierarchy false \
  -jobs 1 \
  -run
```

For an architectural path, replace the target and use its `clock_i` port:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- mac-rx-path \
  -dir _build/xilinx-reports/timing/mac-rx-path \
  -part xc7a100tcsg324-1 \
  -clock clock_i:25 \
  -hierarchy \
  -full-design-hierarchy true \
  -jobs 1 \
  -run
```

The MAC and duplex targets are multi-clock. Specify both actual top-level clock ports:

```sh
./scripts/with-switch.sh dune exec synthesis/xilinx_reports.exe -- udp-duplex-mac-top \
  -dir _build/xilinx-reports/timing/udp-duplex-mac-top \
  -part xc7a100tcsg324-1 \
  -clock rx_clock:25 \
  -clock tx_clock:25 \
  -hierarchy \
  -full-design-hierarchy true \
  -jobs 1 \
  -run
```

`-hierarchy` creates a report project for the selected top and every circuit recorded in
its Hardcaml circuit database. `-full-design-hierarchy true` includes child
implementations in each project; `false` emits them as black boxes for local resource
attribution.

The default profile leaves Vivado free to flatten and optimize across RTL boundaries.
Use `-dont-flatten-hierarchy` only for an explicit attribution or debug experiment, keep
its output in a separate directory, and compare its top-level timing and area with the
ordinary run. It is not the default timing or signoff profile.

To include the complete reports in terminal output, add:

```text
-full-report
```

Vivado defaults to the executable named `vivado`. If it is not on `PATH`, add:

```text
-path-to-vivado /path/to/Vivado/bin/vivado
```

Start with one job. A single Vivado process can consume several gigabytes, while the
reports library otherwise permits several circuit projects to run concurrently.

## Scope and limitations

These are out-of-context estimates. The generated XDC contains only clock declarations;
it does not include the pin, I/O delay, false-path, or asynchronous-clock-group
constraints in `validation/constraints/unified_tx_rx.xdc`.

Consequently, single-clock block and path reports are the most directly comparable.
Multi-clock MAC and duplex reports provide aggregate resource and same-clock internal
timing estimates, but they do not replace the existing Vivado board project for CDC
analysis, MII I/O timing, placement/routing signoff, DRC, or bitstream generation.

The initial integration was tested with:

```text
OCaml:                     5.2.0+ox
Dune:                      3.22.2
hardcaml:                  v0.18~preview.130.106+341
hardcaml_xilinx_reports:   v0.18~preview.130.106+341
Vivado project reference:  2025.2.1
FPGA part:                 xc7a100tcsg324-1
```

The Phase 1 `tx-crc` smoke run produced a compact timing report and standard Vivado
reports. The standard utilization report contained 43 slice LUTs and 32 slice registers;
the compact timing result was 37.493 ns setup slack and 0.260 ns hold slack at 25 MHz.

The upstream runner represents a failed Vivado subprocess as a missing report instead of
making its generated command exit nonzero. This project wrapper compensates by requiring
all three expected report files to exist, be nonempty, and have been refreshed by the
current run before it prints a successful summary.

See `docs/hardcaml_xilinx_reports_plan.md` for the staged adoption plan and the path to
multi-clock and board-level reporting.
